# QLoop 設計書（v1: 日本史年表）

作成日: 2026-10-10
状態: 設計レビュー後の改訂版（配布方式をネイティブ + AltStore から PWA + Cloudflare に変更）

## 1. 背景と目的

- QLoop は 1 問 1 答形式で勉強するためのアプリ。最初の教材（問題集）は日本史の年表で、中学受験（関東圏・易しい〜早慶/MARCH 付属レベル）の範囲を対象にする。将来は高校受験の範囲や他の教科への拡張を見込む。
- 家庭内で使うのが主目的だが、URL を知った人が誰でも使える公開アプリとして配信してよい。無料の範囲で運用する。
- PWA（ホーム画面に追加して使う Web アプリ）として作り、Cloudflare の静的配信から配る。各端末は Safari で URL を開いて「ホーム画面に追加」するだけで導入でき、更新は配信側に置くだけで全端末に行き渡る。署名や再署名の運用は発生しない。
- 利用端末は 3 台（保護者 1 台・子ども 2 台）。端末ごとに成績を持ち、ログインや端末間の同期はしない。学習データは端末の外に出ない。
- 最も古い端末は iPhone 7（iOS 15.8 が最終版）。動作保証の下限は iOS 15.8 の Safari とする。Android や PC のブラウザでも動くが、受け入れ確認の対象は iOS の Safari に限る。

## 2. 機能要件（確定分）

1. 出題パターン A「年号入力」: 出来事を表示し、年号を数字で入力させる。完全一致で正解（複数の正答年を持つ出来事はいずれかに一致で正解）。不正解時は正解の年を表示する（ずれの年数は表示しない）。
2. 出題パターン B「4 択」: 年号を表示し、出来事を 4 択で選ばせる。誤答の選択肢は正解と近い年代の出来事から選ぶ。
3. 出題パターンの選択: セッション開始時に「年号入力 / 4 択 / ミックス」から選ぶ。
4. 出題範囲の指定: 「全範囲」「年号の範囲（ここから〜ここまで）」「時代（複数選択可）」の 3 通り。
5. 復習モード: 最近間違えた出来事を重点的に出題する。
6. 成績: 出来事ごとの正答率を保持し、全体・時代別・出来事別・セッション履歴を表示する。
7. 成績の書き出し（JSON）、読み込み（復元）、リセットができる。
8. データ: 初期データ（年号 - 出来事）は利用者が CSV で用意する（100〜200 件）。4 択の誤答用に追加データを別途作成する。将来は合計で千数百件まで増える想定。
9. 初回表示の後はオフラインでも動く。
10. 画面は日本語のみ。ふりがなは付けない。小学校高学年以上を想定し、通常の大人向け表示でよい。
11. アプリ内でのデータ編集機能は作らない。

## 3. 技術方針

| 項目 | 決定 | 理由 |
|---|---|---|
| 言語 | TypeScript（strict） | 型でデータ形式と状態遷移を固定する |
| ビルド | Vite | 標準的で設定が少ない。`build.target` を `safari15` にする |
| UI | React（最新安定版。関数コンポーネントと hooks） | もっとも標準的で、実装の委譲先が扱いやすい。画面遷移はアプリ内の状態で持ち、ルーティングライブラリは使わない |
| PWA | `vite-plugin-pwa`（Workbox の generateSW） | ビルド成果物と同梱データを事前キャッシュしてオフラインで動かす。更新は `prompt` 方式（6.6 節） |
| 保存 | IndexedDB（`idb` で Promise 化） | 非同期・大容量・索引付き。レコード単位の追記に向く（5.4 節） |
| テスト | vitest（`src/core`・`src/storage`）、Playwright の WebKit（主要な画面の通し確認） | ロジックは Node 上で決定的に検証し、画面は Mac 上のヘッドレス WebKit で確認する |
| 整形と静的検査 | ESLint（typescript-eslint の recommended）と Prettier | 既定設定のみ。独自ルールは足さない |
| 配信 | Cloudflare Workers の静的アセット配信（`wrangler deploy`） | 無料枠で静的配信の帯域は無制限。HTTPS 付き。Pages の後継として新規に推奨されている方式 |
| ブラウザの下限 | iOS 15.8 の Safari | iPhone 7 の最終 OS。これより新しい API は使わない（9.4 節） |

- 乱数は `src/core` の関数に注入できるようにし、テストでは固定シードの生成器を渡す。
- 現在時刻と暦（タイムゾーン）も注入できるようにし、日付境界のテストを可能にする。
- Playwright の WebKit は最新の WebKit であり、iOS 15.8 の Safari と同一ではない。iOS 15.8 固有の非互換は iPhone 7 の実機確認で拾う（各 PR の受け入れ基準に含める）。

## 5. データ設計

### 5.1 出来事（Event）

CSV の列は次のとおり。`core.csv` と `pool.csv` で同じ形式を使う。どちらのファイルにあるかで役割（出題対象 / 誤答専用）が決まる。

| 列 | 必須 | 内容 |
|---|---|---|
| `id` | 必須 | 全ファイルを通して一意な文字列。本番データは `jh-0001` の形式、PR 1〜2 の仮データは `demo-0001` の形式。成績はこの id に紐づく（5.5 節の規則に従う） |
| `year` | 必須 | 整数。0 は不可。紀元前は負数（紀元前 4 世紀ごろ → `-350` など代表年。紀元前 4 世紀は紀元前 400〜301 年） |
| `title` | 必須 | 出来事の文。全ファイルを通して重複不可 |
| `era` | 任意 | 時代の上書き。空なら `year` から時代区分表で決める |
| `approx` | 任意 | `1` なら「ごろ」の出来事。年号入力の出題対象から外し、表示は 5.3 節の規則に従う |
| `alt_years` | 任意 | 追加で正解とみなす年。`;` 区切り。題名全体に対して正解といえる年だけを書く |
| `year_label` | 任意 | 年の表示を上書きする文字列（例 `紀元前4世紀ごろ`、`3世紀`）。空なら 5.3 節の既定の表示 |
| `level` | 任意 | `中学` または `高校`。空は `中学`。v1 では `高校` の行を出題対象から外す（誤答の候補には使う） |

例:

```
id,year,title,era,approx,alt_years,year_label,level
jh-0001,710,平城京に都を移す,,,,,
jh-0042,1185,鎌倉幕府の成立,鎌倉,,1192,,
jh-0300,-350,稲作が伝わる,弥生,1,,紀元前4世紀ごろ,
```

- 利用者から受け取る「年号,出来事」の 2 列 CSV は、`id` を振り、必要な列を足して `core.csv` に整形する（整形は実装側で行い、利用者に列の追加を求めない）。整形後の CSV が正本になり、以後は正本を直接編集する。
- 1 つの出来事に正解の年が 2 通りある場合は `alt_years` で表す。基本は 1 通りで確定している前提。「鎌倉幕府の成立」のように題名が複数の年を許す場合だけ使い、「守護・地頭を置く」のように特定の行為を指す題名には付けない。
- 同じ年に複数の出来事があってよい。

CSV の形式: UTF-8（先頭の BOM は許容）、改行は LF と CRLF のどちらでもよい、1 行目は上の 8 列のヘッダー（必須・順序固定）、「任意」は空セル可の意味で列自体は省略しない、セル内のカンマと `"` は `"..."` で囲んで `""` でエスケープする、セル内の改行は使わない（検出したらエラー）。

### 5.2 検証（`scripts/build-data.ts` とテストで自動確認）

- `id` と `title` が全ファイルを通して一意であること。`id` は `jh-` または `demo-` で始まること。
- `year` が 0 以外の整数であること。`alt_years` が整数で `year` と異なること。
- `era` に書かれた時代名が時代区分表にあること。`approx` が `1` か空であること。`level` が `中学`・`高校`・空のいずれかであること。
- `core.csv` の全行（出題対象）について、4 択の誤答候補が 3 件以上あること（6.3 節の除外規則を適用した後の件数）。
- 検証に失敗したらビルドを止める。データを編集した PR はこの検証で守る。

### 5.3 年の表示と時代区分表

年の表示は 1 か所の関数にまとめ、出題・判定後の表示・まとめ・成績で共通に使う。

- `year_label` があればそれを使う。
- なければ、`approx` なら「○○年ごろ」、そうでなければ「○○年」。紀元前は「紀元前○○年」「紀元前○○年ごろ」。

`era` が空の出来事は、`year` が次の開始年以上で、次の時代の開始年未満なら、その時代に属するとする。

| 時代 | 開始年 | 補足 |
|---|---|---|
| 縄文 | （弥生より前） | 年が確定する出来事はほぼ無い |
| 弥生 | -400 | 紀元前 4 世紀ごろから |
| 古墳 | 250 | 3 世紀中ごろから |
| 飛鳥 | 592 | 推古天皇の即位 |
| 奈良 | 710 | 平城京 |
| 平安 | 794 | 平安京 |
| 鎌倉 | 1185 | 守護・地頭の設置 |
| 室町 | 1334 | 建武の新政を室町に含める。1333 年の鎌倉幕府滅亡は鎌倉に入る |
| 安土桃山 | 1573 | 室町幕府の滅亡 |
| 江戸 | 1603 | 江戸幕府 |
| 明治 | 1868 | |
| 大正 | 1912 | |
| 昭和 | 1926 | |
| 平成 | 1989 | |
| 令和 | 2019 | |

- 南北朝・戦国は室町に含める。旧石器は対象外（初期 CSV に該当行があれば D1 で扱いを決める）。
- 境界の年で表と感覚が合わない出来事（例: 1185 年の壇ノ浦の戦い → 平安、1573 年の室町幕府の滅亡 → 室町）は、データ側の `era` 列で上書きする。
- 時代による範囲指定は、この表ではなく各出来事の確定した時代（上書きを反映したもの）で絞り込む。

### 5.4 成績の保存（IndexedDB）

データベース名 `qloop`、版 1。ストアと索引は次のとおり。

| ストア | キー | 内容 |
|---|---|---|
| `attempts` | `id`（自動採番） | 回答の記録。`eventId`、`pattern`（`yearInput` / `choice`）、`correct`、`answeredAt`（UTC の ISO 8601 文字列）、`sessionId`。索引: `byEvent`(eventId)、`byAnsweredAt`(answeredAt)、`bySession`(sessionId)。追記のみで、これが正本 |
| `eventStats` | `[eventId, pattern]` | 出来事 × パターンの集計。`attempts`（回答数）、`correct`、`lastAnsweredAt`、`lastCorrect`、`lastWrongAt`。成績画面と復習はこれを読む |
| `sessions` | `id`（UUID） | `mode`（`normal` / `review`）、`pattern`（`yearInput` / `choice` / `mixed`。復習は `null`）、`range`、`startedAt`、`endedAt`（未終了は `null`）、`total`（生成した問題数）、`answered`、`correct` |
| `meta` | `key` | `settings`（最後に選んだパターン・問題数・範囲）、`studyDays`（回答のあった端末ローカルの暦日 `YYYY-MM-DD` の一覧） |

- 1 回答ごとに 1 つのトランザクションで、`attempts` への追記、`eventStats` の更新、`sessions` の `answered`・`correct` の更新、`meta.studyDays` の更新を行う。
- `eventStats`・`sessions` の件数・`studyDays` は `attempts` から再計算できる（`rebuild()`）。読み込み（復元）の後に必ず実行する。
- 成績の状態は 1 つの `ProgressStore` が持つ。回答を保存したら同じオブジェクトの中の集計を更新し、成績画面と復習の候補選定はそこから読む。起動時の読み込みは `eventStats`・`sessions`・`meta` だけで、`attempts` の全件は読まない。
- 現在のデータ（`deck.json`）に存在しない `eventId` の記録は保持する。除外するのは `eventStats` から作る表示（全体・時代別・出来事別の成績と復習の候補）だけで、セッション履歴（`sessions` の `answered`・`correct`）と `studyDays` は活動の記録としてそのまま使い、データ更新に伴う再計算はしない。
- `navigator.storage.persist()` が使える環境では起動時に 1 回呼ぶ。効果は保証されないので頼りにしない。
- データベースを開けなかった場合は、理由を表示して学習を始められないようにする（ごくまれなので復旧機能は作らない）。
- スキーマの変更は IndexedDB の版番号を上げ、`db.ts` の upgrade 処理に移行を書く。

### 5.5 id の規則

- id は並べ替え・表記の修正・年の訂正・`core.csv` と `pool.csv` の間の移動で変えない。削除した id は再利用しない。
- 仮データ（`demo-`）は D1 で削除する。仮データに対する回答は 5.4 節の「存在しない id」として扱われる。
- 2 列 CSV の再取り込みが必要になった場合は既存の正本と `title` で照合して差分だけ追加し、全件を振り直さない。

### 5.6 書き出しと読み込み

- 書き出し: `{ "schemaVersion": 1, "exportedAt": "...", "attempts": [...], "sessions": [...] }` を `qloop-progress-YYYYMMDD.json` として出す。ファイル共有に対応した `navigator.share` が使えればそれを使い、使えなければダウンロードリンクにする。
- 読み込み: ファイル選択で JSON を受け取り、`schemaVersion` と形式を検証して、確認ダイアログの後に全置換する（既存の記録は消える）。その後 `rebuild()` を実行する。
- リセット: 確認ダイアログの後に全ストアを空にし、メモリ上の状態も初期化する。

## 6. 出題の仕様

### 6.1 出題対象と適格条件

1. 母集団は `core.csv` のうち `level` が `中学` の出来事（`pool.csv` と `高校` の行は誤答の候補にのみ使う）。
2. 範囲指定を適用する。判定には代表年 `year` だけを使い、`alt_years` は使わない。
   - 全範囲: 絞り込みなし。
   - 年号の範囲: 開始年・終了年のどちらも任意入力で、1〜4 桁の正の整数のみ受け付ける。両端を含む。空の側は開いた範囲。両方空は全範囲と同じ。紀元前の出来事は開始年が空のときだけ含まれる。開始年が終了年より大きいときは理由を表示して開始ボタンを無効にする。
   - 時代: 選んだ時代（複数可）に属する出来事。1 つも選んでいなければ開始ボタンを無効にする。
3. パターンごとの適格条件。
   - 年号入力: `approx` でなく、`year` が正の出来事。
   - 4 択: 6.3 節の除外規則を適用した後の誤答候補が 3 件以上ある出来事（データだけで決まるので起動時に 1 回計算する）。
   - ミックス: 両方に適格なら 1 問ごとに等確率で選ぶ。片方だけ適格ならその形式。どちらにも適格でなければ除外する。
4. 問題数は 10・20・全問から選ぶ（既定 10）。適格な出来事が問題数に満たなければ適格な全件を出す。出題順はランダムで、同じセッション内で同じ出来事は 1 回だけ出す。
5. 適格な出来事が 0 件なら開始せず、その旨を表示する。
6. 問題列と各問題の選択肢はセッション開始時に生成して固定する。

### 6.2 パターン A: 年号入力

- 表示: 出来事の文、数字の入力欄（`inputmode="numeric"`、`pattern="[0-9]*"`）、回答ボタン。
- 入力の正規化: 前後の空白を除き、全角数字は半角に直す。1〜4 桁の数字のときだけ回答ボタンを有効にする。先頭の 0 は無視する（`0710` は `710`）。
- 判定: 整数にして、`year` または `alt_years` のいずれかに一致すれば正解。
- 表示: 正解なら「正解」、不正解なら「不正解」と正解の年（`alt_years` があれば併記）。その後「次へ」。1 問につき回答は 1 回だけ受け付ける（判定後は入力とボタンを無効にする）。

### 6.3 パターン B: 4 択

- 表示: 5.3 節の規則で表示した年（例「1185年の出来事は？」「3世紀の出来事は？」）、出来事 4 つのボタン。
- 正解: 出題した出来事。
- 誤答の候補の除外規則（`core.csv`・`pool.csv` の全出来事から、次に当たるものを除く）:
  1. 出題した出来事自身。
  2. `year` または `alt_years` のいずれかが出題年と一致するもの。
  3. 出題した出来事か候補のどちらかが `approx` の場合、`year` の差が 50 年以内のもの（「3 世紀」と表示した問題に 239 年の出来事が混ざらないようにする）。
- 誤答 3 件の選び方: 候補のうち `year` が出題年の前後 100 年以内のものから 3 件をランダムに選ぶ。3 件に満たなければ、同じ時代の候補、さらに全候補の順で補う（選択済みのものは除く）。
- 4 つの並びはシャッフルする。判定後は正解の選択肢を強調表示し、不正解なら選んだものも示す。1 問につき回答は 1 回だけ受け付ける。

### 6.4 セッションの流れ

1. ホーム → 出題設定（パターン・問題数・範囲）→ 開始。設定は `meta.settings` に保存し、次回の初期値にする。
2. 開始時に `sessions` にレコードを作る（`endedAt` は `null`）。
3. 1 問ごとに回答 → 保存（5.4 節のトランザクション）→ 判定表示 → 次へ。画面上部に「3 / 10」の進捗を出す。
4. 最後の問題も同じように判定を表示する。最後の問題の回答を保存するトランザクションで `endedAt` も記録し、「次へ」の代わりに「結果を見る」を表示する。押すとまとめ画面へ進む。
5. 途中で「終了」を押すと確認の後に `endedAt` を記録してまとめ画面へ進む（回答済みの分は成績に残る）。
6. まとめ画面: 正答数 / 回答済み数（予定の問題数とは区別する）、間違えた出来事の一覧（出来事と正解の年）、ホームへ戻る。
7. 起動時に `endedAt` が `null` のセッションがあれば、`answered` が 0 のものは削除し、それ以外は中断として扱う（再開はしない。履歴には「中断」と表示する）。

### 6.5 ホーム画面からの起動の確認

- iOS で、ホーム画面から起動していないとき（`navigator.standalone` が true でない）は、ホーム画面の上部に「Safari の共有メニューから『ホーム画面に追加』して使ってください」という帯を出す。帯はその起動の間だけ閉じられる。
- 理由: Safari のタブで使い続けると、7 日間そのサイトに触れないと保存データが消える規則があるため。ホーム画面に追加した Web アプリはこの規則の影響を実質受けない。

### 6.6 アプリの更新

- `vite-plugin-pwa` の `registerType` は `prompt`。新しい版を検知したらホーム画面にだけ「新しいバージョンがあります」の帯と「更新」ボタンを出す。押すと新しい Service Worker を有効にして再読み込みする。
- 押さなくても、アプリを完全に閉じて次に起動したときに新しい版になる。学習中に勝手に再読み込みはしない。
- ホーム画面の下部にアプリの版（`package.json` の `version`）を表示する。

## 7. 復習モード

- 成績は（出来事, パターン）の組ごとに `eventStats` に集計されている（5.4 節）。
- 候補 = 現在の母集団（6.1 節の 1）に存在し、記録されたパターンに今も適格で、次のいずれかを満たす（出来事, パターン）の組。
  1. 直近 14 日以内に不正解がある。
  2. 最後の回答が不正解である。
  3. 回答数が 2 回以上で正答率が 60% 未満である。
- 正解した後も、上の条件を満たす間は候補に残る。
- 重み付け: 最後に間違えた日からの経過日数が 3 日以内なら 3、7 日以内なら 2、それ以外は 1。重み付きで重複なく抽選する。候補と重みはセッション開始時に確定する。
- 出題パターンは間違えたパターンをそのまま使う。両方で間違えていれば両方が候補になり、同じ出来事が 2 問出ることがある（許容する）。
- 復習の設定は問題数だけ（範囲指定とパターン選択は設けない）。候補が 0 件なら「復習する問題はありません」と表示する。
- 復習モードの回答も通常と同じく成績に記録する。

日付の数え方（復習と連続学習日数で共通）:

- 時刻は UTC で保存し、学習日と経過日数は端末の現在のタイムゾーンでの暦日の差で求める。3・7・14 日の境界は含む（経過 14 日は「14 日以内」）。
- 「直近 14 日以内に不正解がある」は、`eventStats.lastWrongAt` が端末の現在のタイムゾーンで 14 日前の 0 時以降かどうかで判定する（不正解の記録がなければ該当しない）。`attempts` は読まない。

## 8. 成績画面

1. 全体: 総回答数、正答率、連続学習日数（`meta.studyDays` を使い、今日に回答があれば今日、なければ昨日を起点に、連続した日数を数える。どちらにも無ければ 0）。
2. 時代別: 時代ごとの正答率を横棒（CSS）で表示し、回答数も併記する。
3. 出来事別: 出来事・正答率・回答数・最終回答日の一覧。既定は正答率の低い順。回答数順（多い順）と最終回答日順（新しい順）にも並べ替えられる。同順位は id 順。パターン別の内訳は行を展開して表示する。
4. 履歴: セッションごとに日時・モード・範囲・パターン・正答数 / 回答済み数を一覧表示する。中断したセッションはその旨を示す。
5. 操作: JSON の書き出し、読み込み（復元）、成績のリセット（確認付き）。

正答率の定義（すべて共通）: 対象の回答の正解数 ÷ 回答数。通常と復習を合算する。回答数 0 の出来事・時代は「未回答」と表示し、正答率順では回答済みの後ろに置く。

## 9. ビルドと配布

### 9.1 前提

- Node.js の LTS 版と npm。Cloudflare のアカウント（無料プラン）。
- `wrangler` は devDependency として入れる。初回だけ利用者が `npx wrangler login` でブラウザ認証する。

### 9.2 ビルドとデプロイ

- `npm run build`: `scripts/build-data.ts` で CSV を検証して `deck.json` を生成し、Vite でビルドして `dist/` に出す。
- `npm run deploy`: `npm run build` の後に `wrangler deploy` を実行する。`wrangler.jsonc` は静的アセットの配信だけを定義する（`assets.directory` = `dist`、`not_found_handling` = `single-page-application`）。
- worker 名は `qloop`。公開 URL は `https://qloop.<アカウントのサブドメイン>.workers.dev`。URL を知った人は誰でも使ってよいが、広報はせず、検索エンジンにも載せない。`index.html` に `<meta name="robots" content="noindex">` を置く（`robots.txt` でクロールを拒否すると noindex が読まれず URL だけ載りうるので、`robots.txt` は置かない）。独自ドメインを使う場合は後から足せるが、URL が変わると各端末でホーム画面への再追加と成績の書き出し・読み込みが必要になる。
- 認証（Cloudflare Access など）は掛けない。配信するのはアプリ本体と年表データだけで、学習データは端末から出ない。

### 9.3 版の管理

- `package.json` の `version` を版の正本とし、配布のたびに上げる。アプリのホーム画面に表示する。
- Service Worker はビルドのたびに事前キャッシュの一覧が変わるので、版を上げ忘れても更新自体は配信される。

### 9.4 iOS 15.8 の Safari で守ること

- `build.target` は `safari15`。
- 使わないもの: `ShareLink` 相当のものはない。`navigator.share` のファイル共有は Safari 15 で使えるが、対応判定をしてダウンロードリンクに切り替える。コンテナクエリ、`dialog` 要素の `showModal` は使わない（ダイアログは自前の部品）。
- Service Worker、IndexedDB、Web App Manifest（`display: standalone`）、`apple-touch-icon`、`apple-mobile-web-app-capable` は使える。
- 画面は縦向きの iPhone 幅（375px）を基準にし、横スクロールを出さない。

### 9.5 端末の導入（`docs/operations.md` に手順を書く）

- iPhone: Safari で URL を開く → 共有 → 「ホーム画面に追加」。以後はホーム画面のアイコンから起動する。
- 子どものアカウントの端末でスクリーンタイムの Web 制限が有効な場合は、この URL を許可リストに入れる。
- 更新は配信するだけ。端末側の作業はない。
- 端末の入れ替え時は、旧端末で書き出した JSON を新端末で読み込む。

## 12. 設計レビューで確かめたい点

1. IndexedDB の 4 ストアと「1 回答 1 トランザクション」「`eventStats` は再計算可能な派生データ」という持ち方が妥当か。過剰な部分はないか。
2. iOS 15.8 の Safari の PWA として見落としている制約がないか（Service Worker の更新、ホーム画面起動、ストレージの消去、`navigator.share`）。
3. 4 択の誤答の除外規則（同じ年・`approx` の前後 50 年）と前後 100 年の優先が妥当か。
4. 復習の候補と重み、日付の数え方が「最近間違えた問題を重点的に」の意図に合い、過剰に複雑でないか。
5. 配信（workers.dev・認証なし・noindex・URL を知った人は誰でも使える前提）に、学習データの扱いや運用の面で問題がないか。
6. PR の分割の順序と粒度が適切か。
